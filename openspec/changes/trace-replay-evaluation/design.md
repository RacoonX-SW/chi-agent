# CHI Agent 离线 Trace/Replay 评测设计

## Context

- [`inspect-history`](../../../src/chi_agent/journal.py) 从既有账本与证据重建发送视图，服务于原运行的完整性复核。
- [实验工具](../experiment-harness/specs/experiment-harness/spec.md) 固定对照条件、校验记录并汇总结果。本次新增的是执行用例和定位行为差异的入口。
- [`run_chi`](../../../src/chi_agent/runtime.py) 已接受模型传输 `lower` 与 MCP `server_factory`。[SDK 恢复测试](../../../tests/test_go_chi_recovery_sdk.py) 通过这两个接缝运行实际 SDK 与程序逻辑。[完成核验测试](../../../tests/test_completion_gate.py) 提供 Payer 同案件写后回查的正反例。

## Goals / Non-Goals

- 首版用合成 Payer 场景验证截断、未知写入和完成核验。相同的输入、断言与依赖条件可以在多个源码快照复验。
- 产出用例级派发、读回和完成声明的观测结果，定位首个事件分歧或失败断言。验收分母为本套件实际登记的用例。
- 模型决策质量、任务成功率、真实延迟与 TTFT 由独立的实跑评测测量。正式评测入口、导出包契约及历史账本复核仍按各自的现行规格验收。

## Decisions

### 1. 通过现有接缝执行候选程序

回放入口放在 `scripts/tools/replay_trace.py`。在现有 Python 3.12 开发镜像中，按仓库离线验证的挂载方式使用固定 SDK、MCP 依赖和 CHI-Bench 源码。通过 `httpx.MockTransport` 提供模型响应，通过 `server_factory` 提供模拟 MCP 工具定义与回执。调用 `run_chi` 执行实际 Runner、请求门禁、工具桥、任务状态和账本。模拟只发生在模型与 MCP 的 I/O 边界，检查结果从本次程序的事件和状态得出。

每个用例使用新的合成任务 ID、工作区、账本和日志目录。提供虚构的输入资料与测试标记，在禁网容器中运行。输入来源为合成用例集，现有运行记录继续由 `inspect-history` 只读复核。新工具依赖现有库，供开发验证使用。

### 2. 固定样例并核对请求匹配

用一个版本化 JSON 文件保存首批四个用例，路径为 `tests/fixtures/trace_replay_suite.json`。文件包含唯一用例 ID、角色、运行选项、工具定义、带顺序的模型与 MCP 事件，以及可观测断言。读取一次文件，以同一份字节计算 SHA-256 并解析。运行前校验版本、字段、用例 ID 和支持的响应类型。模拟提供方响应中的截断参数允许保留为字符串，由实际运行时处理。

- 模型边界匹配事件顺序、请求用途与样例指定的稳定字段，例如模型名或已接受工具调用的 ID。请求耗时、随机会话标识和绝对路径不参与对齐。
- MCP 边界匹配工具名与结构化参数。调用的接收计数由模拟服务在返回前记录，结合运行日志区分模型提出、门禁拒绝与实际派发。
- 对齐失败时，先记录首个分歧，再终止该用例的回执供应。预期之外的请求、提前退出导致的事件缺失和未满足的断言各有原因。使用独立状态继续其余用例。

这种匹配允许候选改变上下文内容中与断言无关的字段，同时检查重要的调用关联。原始请求的字节一致性继续由历史复核路径验证。

### 3. 用一组正反例覆盖执行门禁

| 用例 | 从实际执行中观察 |
| --- | --- |
| 截断工具批次 | 原截断调用 ID 未产生派发。恢复请求从已闭合历史重生成。原响应结算记录保留，重生成后的合法调用单独计数。 |
| 写入结果未知 | 首次写入到达模拟 MCP，随后抛出传输超时。状态记录未知效果。下一轮提出的写入被拦截，模拟 MCP 未收到第二次写入，完成声明未被接受。 |
| 写入成功但缺少回查 | 合成案件完成必要读写步骤后，模型直接提出完成声明。断言观察到缺少写后回查的具体拒绝原因。 |
| 写入成功并有效回查 | 与上例共用前置步骤，随后读取同一案件的新状态，再提出完成声明。断言同案读回的顺序与接受声明的结果。 |

截断用例复用现有恢复测试的事件结构，在用例配置中明确启用恢复。写后回查正反例沿用 `test_completion_gate.py` 的 Payer 条件，经运行链中的实际 MCP 和本地工具调用产生状态。以派发、拒绝和声明证据判断用例，预期的程序拒绝或停止可以满足断言。

### 4. 保存报告并对照候选

在配置好的 Docker 环境内执行以下命令。基线和候选分别挂载其固定源码快照，共用调用方提供的 `/out` 输出卷。

```sh
# 在基线快照中执行
python -m scripts.tools.replay_trace run --suite tests/fixtures/trace_replay_suite.json --output-dir /out/replay-baseline
# 在候选快照中执行
python -m scripts.tools.replay_trace run --suite tests/fixtures/trace_replay_suite.json --output-dir /out/replay-candidate
python -m scripts.tools.replay_trace compare --baseline /out/replay-baseline/report.json --candidate /out/replay-candidate/report.json
```

`run` 创建新输出目录并写入 `report.json`。报告记录合成证据类型、用例集 SHA-256、实际运行源码与回放评测器的身份，以及 Python、OpenAI SDK、Agents SDK、MCP 和 httpx 的版本。源码和评测器分别按实际文件的相对路径和字节稳定计算身份，主代理在验收记录中关联 Git 提交、镜像和固定的 CHI-Bench 依赖。事件摘要使用用例 ID、步骤、调用标识、状态、计数和安全错误码，原始模拟数据与工作日志留在该次输出目录。已有输出目录按输入错误处理。

结果逐条保留用例的通过、失败或未执行及原因，并给出计划分母和通过数。`run` 全部断言通过时退出 `0`，有效用例集出现失败或未执行时退出 `1`，输入或输出位置不合法时退出 `2`。

`compare` 只读校验两份报告的版本、用例集与有序清单、评测器身份和已记录的环境条件，允许实际运行源码不同。对兼容报告，按用例返回最早不同的事件或断言及两侧结果，正常生成对照时退出 `0`。输入无效或条件不可比较时退出 `2`。首个实现候选形成可供后续版本使用的基线，先用独立重复运行和受控差异验证对照行为。

## Risks / Trade-offs

- **执行顺序发生变化** → 仅供应与实际请求匹配的回执。报告首个分歧，供维护者判断行为回归或更新用例的需要。
- **拒绝过多导致用例看起来通过** → 检查实际拒绝原因，使用成功写入和读回的正例检验合法路径。
- **模拟结果被用于推断真实效果** → 报告标识合成证据、用例分母与观察对象。实际模型 Token、费用、真实延迟和官方成绩继续使用各自的运行记录。
