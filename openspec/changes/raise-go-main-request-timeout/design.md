# Go 主请求超时与开发复验

## Context

请求守卫分别设置 HTTPX 的读取时间和整个传输的 `asyncio.timeout`。现有 240/300 配置早于 t022 服务端完成时间触发。上批 162 个有响应的主请求 P95 为 45.59 秒，最长 75.96 秒。本次服务端路由重试历时 253.446 秒。

## Goals / Non-Goals

实现已批准的主请求 300 秒读取窗口和 360 秒传输上限。开发批次内，同一候选完成九题各三次独立试跑，按实际端到端结果计分。生产改动限于时间常量、导出配置和策略断言。

## Decisions

1. 保留读取与总 I/O 两层预算的 60 秒间距。整轮开发 runner 外层时间窗口继续作为独立限制。同步源码和配置，按新包身份执行一次 Coding B 准入检查。
2. 本地批次预先绑定 27 个槽位及各自的世界、运行编号和 external 账本。各账本从同一个已验证的 Coding B 证据快照初始化，费用在批次汇总中计一次。每个槽位的运行记录、封存结果和未结算请求持久保存。
3. 本地通过要求运行完成、完成声明被接受且全部适用的确定性检查通过。发出模型请求后发生超时的槽位记录为端到端失败，带上超时诊断和未结算状态。下一槽位用独立的运行世界执行。配额或认证明确拒绝、异常账单来源、证据损坏或残留环境会触发批次诊断。
4. 27 个真实试跑终结后，`pass@1` 为通过轮次除以 27，`pass³` 为三轮均通过的题数除以 9。先前评测记录和本轮新候选分别绑定自己的包身份。

## Risks / Trade-offs

读取等待可比当前延长 60 秒。非流式响应的总耗时继续来自接收完整响应的时间。超时槽位的实际用量或费用可能稍后由服务端提供，批次先保留已知前缀和未结算项。
