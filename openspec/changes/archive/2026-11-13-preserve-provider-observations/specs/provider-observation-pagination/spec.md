# Provider observation pagination

## Purpose

使 Provider 身份确认能从有界工具结果验证完整候选名单与相似候选病历，同时保留原始观察、患者绑定及写入归属的证据链。

## ADDED Requirements

### Requirement: 交付完整名单的有界页面

Provider Go SHALL 将符合条件的完整无筛选患者搜索交付为按原始版本绑定的精简名单页。页面 SHALL 保留各候选的身份核对字段及真实覆盖范围。

#### Scenario: 名单超过普通列表裁剪数量

- **GIVEN** MCP 在单次无筛选搜索中返回 65 个不同候选。
- **WHEN** Provider 获得用于身份确认的名单。
- **THEN** 精简字段后保留 65 个候选。单页装不下时可从返回的下一页偏移读取同一原始版本，直至全部候选被覆盖。

#### Scenario: 搜索只返回筛选结果或不完整的名单

- **WHEN** 搜索带身份筛选条件，或返回项目数小于名单总数。
- **THEN** 结果沿用普通搜索的交付方式。该结果不能建立完整名单。

### Requirement: 交付可验证的病历原文页面

Provider 病历读工具 SHALL 依据序列化大小在既有单结果预算内返回原文区间及接续位置。派发器 SHALL 将已定长的页面原样交付。

#### Scenario: 病历内容或 JSON 转义跨越单结果预算

- **WHEN** 模型从一个有效的病历偏移读取原文。
- **THEN** 工具返回一个满足字符和 UTF-8 字节上限的完整 JSON 页。页面带原文哈希、起始偏移、总长度和实际的下一页偏移，最后一页的下一偏移为空。
- **AND** 逐页读取能无缺口还原该版本病历，且模型收到的页正文与派发记录一致。

### Requirement: 以实际交付验证覆盖与写入归属

Provider 确认 SHALL 检查候选名单及相似候选病历的版本、原文和已交付覆盖。达到完整性要求后，现有语义确认和归属校验决定后续写入资格。

#### Scenario: 页面跨请求完整交付

- **WHEN** 当前名单和所需病历页面已实际交付，且其内容与当前原始工具观察相符。
- **THEN** 程序允许进入现有语义确认。只有确认结果支持唯一患者且写入归属通过时，案件操作才会派发。

#### Scenario: 页面缺失、过期、内容不符或候选仍有歧义

- **WHEN** 页面覆盖不全、版本已更换、内容与原始观察不符，或语义确认仍存在不确定候选。
- **THEN** 程序保留未绑定状态，并记录相应拒绝。案件写入仍受患者绑定门禁拦截。
