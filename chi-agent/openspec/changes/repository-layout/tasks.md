# 实施与验收清单

按 [增量规格](specs/repository-distribution/spec.md) 验收，文件去向及兼容约定见 [设计](design.md)。

## 1. 固定基线

- [ ] 1.1 核对用户批准的提案提交和范围，将依据记入 proposal.md。核对分支基线、原 checkout、工作区和实际远端，确认固定历史提交包含整理前的源码及证据。
- [ ] 1.2 在 Docker Python 3.12 用一次完整 pytest 收集基线适用用例，另跑 controller 专项。记录结果、已知跳过项、镜像与卷。用固定源码快照生成两种 v1 验证样本，存放于临时目录。

## 2. 铺平项目与分类命名

- [ ] 2.1 迁移设计中指定的跟踪文件与 OpenSpec 根，合并 Git 和 Docker 忽略规则。检查移动前后的 Git 文件清单、执行位、忽略规则及两份 Compose 的 `config --quiet`。
- [ ] 2.2 按表迁移 72 个脚本。更新限定导入、动态加载、命令参数中的脚本路径、代码身份清单与测试。核对 72 个唯一源和目标，验证根目录模块入口及开发镜像中的导入。
- [ ] 2.3 更新 A 阶段 Compose、统一操作者、旧操作者、角色 runner 和 CM 患者模拟的绑定映射。用现有角色配置和跨容器合成检查验证入口、`dev_sha256`、角色资源与清理边界，检查文档命令与挂载一致。

## 3. 更新导出与兼容校验

- [ ] 3.1 更新两种显式打包清单，加入按职责命名的包目录和稳定启动文件。用导入检查核对两份包的依赖闭包、成员与源码对应关系。将完整 pytest、controller 专项及两种包的校验和隔离预检接入 `verify_offline.sh`。
- [ ] 3.2 用固定清单区分两代 bundle，更新 release 校验和内层包成员复核。验证基线 v1 样本和新 v2 包的身份，测试未知版本、错配清单、额外文件、符号链接和篡改。
- [ ] 3.3 精简两份运行手册，保留当前运行和导出所需命令。用干净导出目录、固定依赖与 vendor 只读挂载复验 Go `preflight --bundle-sha256` 和兼容评测 `preflight`。检查 Go 返回 `identity_verified`，兼容评测达到 `technical_ready`，并保持其 `live` 模式的现行拒绝行为。

## 4. 收敛默认分支文档

- [ ] 4.1 根 README 展示累计开发覆盖、最新六题基线与 Docker 快速开始。核对三领域数量、`16384` 配置、完成声明、历史检查与 `official_reward=null`，通过 OpenSpec 中的一个成果证据索引追溯原报告。
- [ ] 4.2 核对 `docs/` 仅有两份运行手册，`AGENTS.md` 提供现行协作入口，`openspec/` 保留审核状态、在用规格与未决事项。验证受迁移影响的链接，并从固定提交抽查学习材料、原验证记录和审批。

## 5. 干净检出与独立复验

- [ ] 5.1 在干净检出中执行 README 的 Docker 快速开始，再用一次统一离线入口验证开发回归、controller 和两个导出包。复用本次隔离启动结果完成 3.3 的验收，并执行合成 Harbor 预演。验证结果、已知跳过和环境限制集中记录于 PR。
- [ ] 5.2 固定候选并独立审阅差异，核对上传和导出成员、旧包及原始账目边界。复核新候选的验证身份与六题历史证据分别对应的提交和包，检查 OpenSpec 严格校验。

## Workflow follow-up

- 在最终 PR 分支同步本变更的规格并归档，核对归档后的规格和路径。
- 将验证结果写入面向 `main` 的 PR，注明旧包兼容范围、新包身份和实际验证缺口。用户审核并决定合并。
