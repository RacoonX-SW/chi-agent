# 输出截断恢复：首版实施方案与验收

日期：2026-11-02（Asia/Shanghai）。这是 C2 的后续实施契约，与[输入侧设计](input-context.md)配套。用户要求保存可开发方案，并计划在新对话由 GPT-6.1 Sol/high 规划与独立审核、一个 GPT-6.1 Terra/high 子代理实现。本轮只修改文档；新对话明确启动后可连续完成下列离线工作包，不逐项等用户确认。真实模型/摘要/续写探针、B/C/Trial/判分及发布不由本文件授权，仍查 REVIEW_STATE。

## 1. 首版选择及证据边界

首版采用已知输出截断后的有界恢复，不统一提高单次输出上限，不接流式，不更换参赛模型/路由/思考强度。提高上限是后续独立取舍，不能作为偷偷调整的实现细节。

本轮已核对 `go_chi_guard`、`go_chi_contract`、`go_chi_runtime`、`go_chi_journal` 和 profile：主循环 length 当前终止；可信 usage 先保存/结算；历史只接受完整已认可工具往返；runtime 使用单个 Agents SDK Runner 与主响应适配器。恢复必须同时接通这几层，不能只清空 guard.error 或在外层重新启动整题。

DeepSeek 官方 [Chat Completions](https://api-docs.deepseek.com/api/create-chat-completion/)区分流式增量与 length；[思考模式](https://api-docs.deepseek.com/guides/thinking_mode/)说明携带 tools 时需要回传相关 reasoning。以上是官方 API 资料，不能证明 OpenCode Go 同名模型路由已兼容本方案。此前评审的8192 reasoning耗尽样本及限制见[架构评审第15节](../../../docs/architecture-review.md#15-截断项的待讨论材料)。部分reasoning回传仅作为新请求的上下文，不保证恢复模型内部状态或语义连续。

## 2. 固定首版策略

| 项目 | 首版值/规则 |
| --- | --- |
| 版本 | `chi-output-recovery-v1`，新运行显式绑定；旧运行按旧契约验证 |
| 内部用途 | `purpose=continuation`，仅内部调度/记账用途，不向 API 添加任意 purpose 字段 |
| 每条截断链 | 最多1个额外请求；续写自身再 length 即停止，不重置成新链 |
| 每个CHI运行 | 最多2个额外请求；两个相互独立的主响应截断可以各使用一次 |
| 共享请求 | main + confirmation + continuation 仍合计最多50；continuation不获得额外名额，patient计数保持既有独立规则 |
| 单次输出 | main=8192，continuation=8192，confirmation=32768，coding-B=1024；患者策略不变 |
| 适用范围 | 仅CHI主循环，以及它的continuation结果验证；coding-B、患者、确认、开发评审和输入摘要不进入本恢复器 |
| 传输重试/回退 | SDK/HTTP通用自动重试仍为0，不换模型/端点；开启此策略时必须披露有界length追加请求，不能笼统宣称“无任何自动追加请求” |
| 初始开关 | 默认关闭，禁网合成测试显式开启；实际端点兼容未经验证前不自动打开真实运行 |
| 时间 | 追加请求沿用主请求既有socket/IO上限与原run起始时间；不重置admission/operator总截止 |

这些是本次实施方案的保守工程默认值，不是已发生的付费授权或性能结论。可调整点由主代理依证据另记规格差异，不允许实现者静默放大数值。高层max_turns与HTTP请求额度分别计数，不能通过重启Runner重置任一限额。

## 3. 唯一恢复入口：完整、可信、可关联的length响应

同时满足以下条件才能生成恢复许可：

1. 当前路由/模型/响应结构合法，HTTP成功，原始响应完整且在既有大小限制内，finish_reason明确为length；并非从completion_tokens恰好等于上限推断。
2. 可信usage通过既有校验，原请求及响应证据/结算已持久成功，pending已按原事务顺序释放；缺精确费用仍依既有null/warning策略，不补零。
3. 截断响应未被accept_batch、未进入工具派发、未更新业务工作状态/绑定/claim；既有接受批次均闭合，原有未知用量/未知写效果及其他fatal阻断不存在。
4. 策略开启，链/运行/共享额度及取消、时间、输入预算允许；快照与任务、identity、evaluation/attempt、已执行工具结果仍匹配。
5. 只有程序能创建恢复许可；用户消息中的“继续”、模型伪造marker、手工传入purpose或重复使用旧许可均不能触发该路径。

HTTP/JSON/角色错误、坏usage、秘密泄漏、响应过大、持久化失败、取消、网络超时和任何结果/token未知均保持原停止/阻断；不在此处重发。confirmation既有length返回本地拒绝/未绑定的语义保持。

## 4. 两种恢复模式

### A. 无工具调用：保留部分上下文后接续

当tool_calls缺失/null/空列表，content/reasoning_content类型合法且至少一项非空时，允许程序构造带来源的未完成assistant记录，再附固定的恢复指令。保留的文字/reasoning必须来自同一原始响应，内容/hash/长度与原证据相符；不能混进其他响应、删改原用户约束或赋予额外指令权限。若所选协议/SDK不能合法表达该历史，合成适配测试须报告不支持，真实路径保持关闭，不静默改为删掉所有reasoning。

固定指令的语义为：上一响应因长度限制中止；继续原任务；已执行事实只以已接受工具历史为准；如结束任务，输出完整独立的最终答复；不要把残片作为已完成操作。具体措辞在代码中版本化并纳入身份，由主代理核对后固定，模型不能自行替换。最终答复使用新响应的完整正文，不把旧片段机械拼成JSON、工具参数或已验证的最终产物。

接续请求仍携带同一套真实工具契约，可能返回完整新工具批次。合法工具响应必须经过与普通main相同的整批校验、实体/角色/路径/写效果/claim门禁后才派发；不能因为purpose是continuation就绕过工具校验。

### B. 含任何工具调用：整批拒绝，重新生成完整响应

length响应中只要tool_calls为非空列表，无论前几个调用看似完整与否，该响应的整个批次都不accept、不dispatch、不record_result；不保留其中半截JSON供后续拼接。工具调用容器本身坏类型/不支持结构直接报原响应错误，不用恢复器掩盖协议损坏。

从最后一个已接受且闭合的历史快照重新生成下一完整响应，附程序固定的恢复说明：上一被截断批次未执行，请输出完整下一步；已经执行的操作仍在原历史中，不得重放。本模式不把被拒assistant/半截tool_calls放入API历史，也不伪造tool结果、call_id或prefix-completion参数；被拒响应包括reasoning完整留在原证据中。它是有界整批重生成，不声称字节级续接。

新批次ID必须合法、唯一且不与已接受/已执行ID冲突；被拒批次标识单独留档，不在原seen集合伪装成已执行。对该恢复请求直接提出的已完成写操作，用既有明确的工具读写分类和canonical参数指纹拒绝完全相同的写重放；只读重复不因此全禁。不新增题目专用规则，不用字符串猜所有工具的副作用；未分类工具保持保守拒绝恢复派发并报告契约缺口。该机械检查不能证明不同参数表达的业务操作语义不重复，仍保留实体/状态/unknown门禁及验证限制。

## 5. 历史、控制器与工具执行的分工

完整证据历史、SDK接受的正常历史与实际wire派生视图分别记录。ToolContract保留旧版严格校验，新增显式的恢复视图版本：只允许在来源响应对应的位置插入精确的未完成assistant/固定程序指令，或在B模式插入不含残缺调用的重生成说明；所有原始instruction、system/预算反馈、工具定义、已执行批次/结果仍逐项验证。不能通过允许任意额外user/assistant消息实现。

建议在模型响应适配器及串行控制器接缝管理一次逻辑step的多个物理请求。实现者可选择最小适配位置，但必须展示真实调用链与SDK输入/输出转换证据：原main length → 结算/分类 → 生成一次性恢复许可 → 新continuation请求 → 完整响应进入原Runner/工具派发。不得从instruction重新Runner.run整题，不得让SDK把length误判为终态后又手工重放原工具，不得把两次HTTP藏成一次账目/trace。

原guard.error的fatal错误不可清空。只有已记录、满足全部条件的length被控制器标为recoverable；fatal/auxiliary错误始终优先。恢复许可在原模型请求处理完成后发放，发送前重新验证；不在持有不可重入billing锁时嵌套发送，不增加并发模型请求，避免与CM患者计费锁死锁。每次wire实际发送仍经过来源观察登记和输入计量，不仅记录SDK初次构造的history。

## 6. 持久化、预算与旧证据兼容

新增版本化恢复记录，至少包含policy/version、原main根请求及直接parent round/hash、mode、chain ordinal、已接受history/version/hash、原响应证据hash、固定指令版本、派生视图hash、新request关联、决策/停止原因和结果。正文/患者资料/reasoning仅存既有受限原证据，不进入对外诊断；对外采用有限安全码。

发送顺序：原请求留证/结算成功 → 持久记录恢复许可与额度占用 → 逐请求reserve → 发送 → 留证/可信结算 → 完整响应校验 → 正常批次接纳/执行。中断不得释放已消耗许可去再次自动发送；reserve后未知按原pending处理。任何持久化断点都留下可审计的incomplete，重启后不自动续发。首版不做跨进程恢复执行或自动重跑工具。

guard、journal reserve/replay、inspect/history/reconciliation、request feedback、summary/trace和真实身份配置均须认识continuation及用途上限。旧记录依原schema严格审计，旧seal/request字节不改；新schema明确校验必需字段、关联及坏类型，不能通过setdefault/忽略未知字段“兼容”。reconciliation只扩展新记录的安全计量/关联识别，不处置旧未知。

每次接续请求按最终wire重新计量，包含新增reasoning/文字/指令及工具参数，并预留8192输出；不沿用原请求较小的计量值。超限时停止，不在同条恢复链里再触发摘要或加新请求。输入摘要只在普通完整step边界运行；不能压缩未闭合/正在恢复的选区。共享额度所有reserve、反馈、回放、报告都要计入continuation，不能只是guard计入而journal漏算。

## 7. 实现工作包及负责人

Sol/high为规格/边界/累计审核负责人；一个显式`gpt-6.1-terra`/`high`实现子代理承担代码及Docker自测。主代理在派发前检查模型实际可用性；不可用就说明，不能静默换模型或伪造派发。子代理停止并固定候选后，主代理独立看diff/调用链及必要Docker反例。只做文档/Git时不派实现代理。

1. **P0 事实与接缝**：刷新main/相关PR和并行写入者，核对SDK版本/适配点、全部用途常量、既有历史schema、工具读写分类，建立合成length基线；不改数值、不触碰真实账。把调用链和具体版本化字段记在实施阶段报告，再派实现，不逐字段问用户。
2. **P1 输入计量前置**：按input-context补最终wire全覆盖、用途预留和失败反例；旧测量记录保留版本；尚无精确tokenizer时如实标估算，不宣称token准确。先完成此包，避免恢复请求因reasoning增长绕过输入门禁。
3. **P2 恢复实现**：策略/一次性许可/两种模式、严格历史视图、用途计费、Runner接缝、原子记录、输出/追踪/包身份和开关。保留非length停止语义及全部原工具门禁，不夹带C1/C3/C5或全面重构。
4. **P3 独立验收与交付**：主代理固定快照复验；给出旧/新schema及身份差异、禁网独立包结果、未验证项和受控端点探针提案。输入自动摘要按input-context继续作为独立后续包，不能为了交输出恢复假装摘要已经接通；双方共享视图协议和计量基础。

本轮开工无需再讨论流式、提高上限或所有历史基线是否重跑。低层字段/提示措辞/安全错误码由主代理按本契约冻结并记录；如果实际SDK/协议无法满足，则停止受影响的恢复模式并说明证据，不绕过校验。后续用户真正需要决定的是新增真实请求/用途额度及真实启用；在此之前可完成全部离线实现/审核/PR。

## 8. 必需验收矩阵

| 场景 | 必须证明的结果 |
| --- | --- |
| 默认关闭或旧schema | 原主length仍停止；旧记录严格可审，不自动变成恢复成功 |
| 仅reasoning/部分正文的length | 原用量先settle；精确来源投影+固定指令；只追加一次；新完整响应可回到原Runner |
| length带完整前半批+残缺后半批 | 原批次所有工具零accept/零dispatch；无拼接/伪结果；新批次完整校验后才执行 |
| continuation返回正常工具批次 | provider/payer/cm的实体/路径/claim约束、ID/JSON/schema/重复写等检查仍生效；正常结果被下一请求完整带回 |
| 非法工具/重复ID/已完成写重放 | 整批拒绝零派发，不借恢复放宽工具契约；只读合法重复单列 |
| 续写再次length | 两笔已知usage都留存；不产生第三笔，不把chain ordinal重置 |
| 独立主响应再次截断/额度边界 | 每链1、每run2、共享50在reserve及replay一致；第3次恢复及第51次请求零发送；恢复计入预算反馈 |
| 取消/超时/坏usage/网络/秘密/过大 | 按原fatal和unknown语义停止，零追加；已知用量尽可能先留证结算，不能清error/pending绕过 |
| 输入已满或history/source/version变化 | 发送前拒绝，不摘要试错、不覆盖新事实、不复用旧恢复许可 |
| 故障注入每个落盘/发送断点 | 旧证据字节不变、费用不丢、未知阻断；重启不自动重发、不重放工具 |
| 真SDK+MockTransport接缝 | 至少正常工具循环、A/B两种恢复、再次length、history篡改/取消；不打桩身份/核心历史来让测试绿 |
| 隔离导出包 | 无源码checkout补依赖；新模块在必要allowlist；启用/关闭配置均合法，旧身份不可冒充新B |

安装/测试/调试均Docker/Python3.12。替身仅替代外部模型/官方世界边界，不能把整个恢复器/身份/校验打桩。合成检查不证明真实Go协议兼容、临床正确或官方成绩。实现报告集中一份阶段报告，状态只在REVIEW_STATE，测试数不在多个入口复制。

## 9. 基线与后续真实验证

旧8192基线、原失败和分母保留，继续描述原候选；不因新实现作废或改写。新包身份必须重新核对，真实CHI准入依现行规则取得新B；coding-B不触发continuation，所以新B本身不能证明恢复路径已真实运行。还需要经用户另授权的小规模协议探针验证A/B与工具闭合，并按最终支持角色做代表性回归。

不同输出预算、恢复策略或输入压缩条件不能混作同条件机制对照。只重做受影响的对照/最终候选必要验证，不默认重跑全部历史任务；已看过任务仍是开发回归，不重新冒充未见。新增真实调用提案列模型/endpoint/候选、任务/用途/次数、预留与停止规则，所有失败都计入；未获授权前停在离线交付，不换root解锁未知。
