# 竞赛路线与 OpenSpec 变更顺序

阶段、授权、已通过身份及下一步统一见 [REVIEW_STATE](../reviews/REVIEW_STATE.md)。单题本地执行与 L 评审闭环后，按 [两个新任务的固定条件基线](changes/provider-two-task-baseline/proposal.md) 检查同一 Agent 的新任务表现；复用现有循环和评审，模型替换的结果与官方 Claude 分数分开。旧尝试/账目保留，正式入口 record_only/null cap 与 F.5 最终冻结边界延续。实现分工按 [当前工作流](../docs/subagent-workflow.md)，不操作 Antigravity。

本文件用于协调变更顺序；具体行为契约写入各变更的 `specs/`，实现取舍写入 `design.md`。尚未决定的 Agent 改进策略不提前写成已冻结需求。

所有阶段同时遵循 [学习约定与进度](../docs/learning-agreement.md)：结合真实材料/源码/轨迹，串起阶段目标、设计、调用链与验证，默认不安排小测。教学是协作要求，不改变比赛的自主评测规则，也不把完成课程设为开发前置条件。

2026-10-21 的 [开发讨论](../docs/development-discussion-2026-10-21.md) 补充了官方能力与自有实现的分工、已核对的工具调用示例及各阶段证据。它是规划说明，不代表模型、harness 或改进策略已经冻结，也未恢复实现。

## 截止前排期（2026-10-28提案）

已重新通过浏览器读取当前 Rules，官方日期与必交材料见[竞赛要求](../docs/competition-brief-2026-10-20.md#当前截止时间与费用)。建议把 **11 月 6 日设为内部可提交版本里程碑，11 月 13 日前完成实际交付**，其后留缓冲。下列为讨论中的排期，具体接入/冻结仍按有界变更执行；本次规划不解除正式入口、原版 Claude 判分或 F.5 的现有暂停，不自动开新付费阶段。

| 日期（北京时间） | 工作重点 | 完成标准 |
| --- | --- | --- |
| 10/28–10/29 | 收尾 P：必要新 B、至多一次 t013 C/检查/开发评审，t019 付费暂停 | 根据完整证据决定保留或调整字段提示；保留失败，不把全通过作为转入交付准备的门槛，不围一题无限重跑 |
| 10/29–11/1 | 正式可运行入口与提交包接入，复用 G/H 已有基础 | 接受主办方 instruction/MCP/logs/凭据注入，接入经过选择的 K 改进，源码与配置不绑定开发题或本机账目；独立目录/失败路径离线演练通过 |
| 11/2–11/3 | 正式入口实际运行与小规模迁移检查 | 优先用同一次 C 运行一题未用于调参的兼容 provider 任务，兼顾真实入口和未见题证据；先冻结任务/配置，完整留证。三赛道启动/协议离线检查单列，不把它们写成业务已实测 |
| 11/4–11/6 | 形成内部可提交版本并冻结 | 从独立导出包复现，模型/提示/依赖/预算策略/入口固定；Writeup、包、报告均有完整首稿，报名/队伍状态在其截止前核对，已知缺陷和验证边界写清 |
| 11/7–11/10 | 报告、Writeup 与复现材料完善 | 从已有成功/失败/费用证据写结果与局限，补齐运行说明/模型标识/外部资源，核对报告页数，禁止把本地 verdict 写成官方 reward |
| 11/11–11/13 | 最终材料审核并交付 | 包排除秘密/手册/开发账目，独立启动证据可查；材料可具体审阅，发布/私有发送按用户最终授权执行，保留交付记录 |
| 11/14–11/15 | 缓冲 | 仅修阻塞运行、材料或交付的问题，避免引入未经验证的大改 |

正式入口是当前关键交付缺口：`evaluation_entry.py live` 仍明确拒绝真实执行，G/H 只证明相应离线接点；本地 K 跑通不等于提交包已可运行。下一正式接入须核对现有模型/工具/凭据与官方入口契约，按独立规格实现与审核，不能只去掉暂停判断。复用现有镜像、锁和 SDK/PDF 卷，不默认重做已通过的 G/H 安装；运行平台或依赖确有变化时，补必要的针对性复现。

当前真实业务证据集中于医院侧，比赛总排名覆盖三赛道。短期先确保同一冻结系统能接收各角色的公开输入和工具，明确通用循环与角色约束的适用范围；保险方/照护管理的业务能力及额外模拟器依赖需单列，未经实际验证不宣称三赛道通过。现有 PA provider 开发评审契约不能直接冒充其他领域的判分。

用户已选择新增约 50 元 DeepSeek 开发 API 费用作为规划范围，现行授权/账目口径只见 REVIEW_STATE。建议以下预留，**不是单次硬上限，也不修改 record_only/null**；金额均是安排实验的估算，不是账单或固定价格：

| 用途 | 建议预留 CNY | 调用安排 |
| --- | ---: | --- |
| t013 收尾验收及对应必要探针/评审 | 15 | 一次 C，先离线与当前源码 B |
| 正式入口与未见题合并验收 | 15 | 一次 C，任务/契约兼容后才安排 |
| 有明确故障依据的必要复验 | 15 | 最多一次 C，可不使用；不为刷全通过重跑 |
| 额外探针、评审与用量波动余量 | 5 | 按证据使用，不默认花完 |

完整 C 暂按最多三次安排，不给 t019 例行付费重跑或全量 75 题预留；实际某次用量明显增加时，先压缩后续可选实验并重排。每个改动先离线验证，固定有审核证据的候选后才调用，相关实际调用遵守文档时段规则。未知用量继续阻断，旧账/失败/claim 保留；DeepSeek 预算不包含 Codex 开发代理用量，也不自动授权 Claude 模拟器/判分。

## 阶段 0：理解官方任务（本轮已完成只读拆解）

- 先看 [头痛新转诊任务拆解](../docs/task-walkthrough-pa-t018.md)：输入、静态工具、示意流程、环境限制、评分来源和未知项。
- 本阶段核对官方输入、8 类 30 个静态工具及基础超时；后续实时接入的证据另见 A 审核，不由静态拆解推断。
- 不提供隐藏答案，不凭静态说明填写 task reward，不把单题开发案例当作未见验收集。

## 阶段 1：可信的单任务接入与开发执行

沿用 `changes/bootstrap-baseline/`，不另建重复的基线实现任务。

- 规划任务固定为 `pa_t018_t018_o001_p01_new_referral_provider`，代码和数据分别固定版本。
- 按 D0/A/B/C 核对容器开发环境、角色工具和单任务入口；参赛模型与官方参考 runner 的组合仍是待实测候选，凭据的实际可用性未验证。首轮模型工具接入和一次任务尝试共 5 元已由用户确定，写代码费用另记；预算选择没有恢复付费运行。
- 用户暂缓本地 Anthropic 判分，先验证离线检查、真实工具接入与无评分执行，保留轨迹、版本、状态回读与可信资源记录。具体无评分入口须验证，不能捏造 CLI 参数。
- 官方判分保留为暂缓项；reward 为 null，不能宣称任务已通过或产生竞赛通过率。部分 Claude 模拟对话同样需要单独检查依赖。
- 以后若执行官方判分，保留原版 reward 和 scorecard；有效 0 分也是真实测量，不能宣称解决任务。详见 [开发准备](../docs/development-preparation-2026-10-21.md)。
- 每次恢复按当前审核身份增量核对差异，历史未通过报告只作为对应缺陷的证据，不覆盖后续独立验收。
- B 离线探针用合成响应和合成工具检验请求/历史、关联、预算与失败处理；其通过不代替选定 provider/官方 runner 中的真实连续往返。接入层离线开发见 [设计记录](changes/bootstrap-baseline/design.md#模型与官方-runner-接入层本轮设计)，真实 B/C 仍需另行恢复和验证。

## 阶段 2：根据实际执行证据提出 Agent 改进变更

真实执行后，再决定改模型、规则查阅、工具选择、材料生成或流程控制中的哪一项。工具错误、漏操作、超时等工程问题可以先依据轨迹修复；没有官方分数时，只报告工程诊断，不声称提升了官方成功率。每轮提出独立、可验证的行为变更，不预选网页、编排框架、多 Agent 数量或检索架构。

可参考 [执行循环设计讨论](../docs/agent-loop-discussion-2026-10-21.md) 中的模型/程序分工、运行状态和结束检查候选。这些是待验证的设计方向，不提前当作已实现能力，也不扩大首个 bootstrap 接入变更的实现范围。

改进应可用于同类新任务，不硬编码任务 ID 对应的答案、终态、表单值或文档产物。对照运行固定任务、模型和可比预算；更换模型时单独记录变量。

M 的两个新任务固定条件基线揭示了目标案件局部检查以外的错患者副作用，[N 患者确认与绑定](changes/provider-patient-binding/proposal.md) 据此增加公开证据确认和跨患者写入门禁，再以原两题作开发回归。M 原始发现见 [M 报告](../reviews/provider-two-task-baseline-review.md)，改进证据、仍未解决的运行收束及下一实验建议见 [N 报告](../reviews/provider-patient-binding-review.md)；不能把局部 verdict 当完整任务成功，也不把已见题回归写成新的泛化证据。

[O 请求次数反馈](changes/request-budget-awareness/proposal.md) 接续运行收束问题：在 K 自主 C 使用 50 次共享请求契约，并在每次主调用前提供可信剩余信息，保留患者门禁与原完成工具语义。该组合变化的独立审核、真实回归及限制只见 [O 报告](../reviews/request-budget-awareness-review.md)，不把正常退出自动当作业务成功。

[P 字段依据提示](changes/referral-field-guidance/proposal.md) 从 t013 的字段选择继续改进现有建案/提交工具指导。按用户成本取舍，先离线验证，t019 暂停付费重跑，t013 优先；提示接入与真实业务有效性分别确认，详见 [P 报告](../reviews/referral-field-guidance-review.md)。

## 阶段 3：跨领域、小批量与必要并发

逐步纳入医院侧、保险方和照护管理的代表任务。批量与并发是评测组织方式，不等于为每道题写专用 Agent。任务清单和调用数量依据实际资源与预算决定，不把全量 75 题当作参赛资格条件。

## 阶段 4：冻结可复现参赛材料

按 Kaggle 当前 Rules 准备 Writeup、私有可运行程序包和 IEEE 双栏技术报告。模型、接口、提示词、配置和依赖身份可复查，公开实验结果对应真实官方证据。受限手册和凭据不进入提交包。

最终排名由主办方使用冻结系统在私有任务上的评测决定。独立 evidence leaderboard 和完整公开审计包为当前规则注明的可选项。规则及提交流程在交付前复核。
