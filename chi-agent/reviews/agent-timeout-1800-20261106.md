# Agent timeout 1800s：官方依据、改动与验证

日期：2026-11-06（Asia/Shanghai）。分支：`deepseek/agent-timeout-1800`，基线 `origin/main=8154148`（PR64 已合并）。**本文件记录一次开发路径的时间策略调整，不是正式 Harbor 运行授权，也不声称官方分数。**

## 1. 官方依据

| 来源 | 值/语义 |
| --- | --- |
| t015 `task.toml` | `[agent] timeout_sec = 900.0`；`[verifier] timeout_sec = 1200.0`；`[environment] build_timeout_sec = 1200.0` |
| 官方 `SubmissionRun` | `timeout_multiplier` 默认 **2.0**；`agent_timeout_multiplier` 默认 `None`（`vendor/chi-bench/src/chi_bench/experiment/submission.py:121`） |
| 官方实验配置 | `table1`–`table5`、frontier 配置统一 `agent_timeout_multiplier: 2`（如 `configs/experiments/table1_main_matrix.yaml:11`） |
| 官方测试 | 多处断言 `agent_timeout_multiplier == 2.0` |
| 竞赛规则 | “An agent timeout … normally produces a failed trial”；只有主办方基础设施故障才可能重跑（`docs/competition-rules-draft.md:177`） |

结论：**task.toml 的基础 agent timeout 是 900s；官方 submission/实验默认乘 2，有效上限为 1800s。** 我们原先的 `chi_admission_seconds=900` 只对齐基础值，比官方默认更严；调到 1800s 与官方默认一致，**不应超过 1800s**。

**边界**：Kaggle 实时 Rules/Overview 是最终权威，私有评测配置由主办方控制；本地官方仓库对齐到 2026-10-06。若主办方不加 multiplier，900s 才是硬上限。本调整按官方仓库默认 2× 实施，并在报告中如实标注。

## 2. 为什么调整

- t015 的 900s 重试 `final-c-provider-t015-retry1` 已运行到 942s，23 个请求全部 settled、无 pending/halt；模型已创建 case、写入大部分 new-referral 字段，只差最后的业务状态回读/provider determination，被 `chi_run_time_limit` 切断。
- 该失败不是 API 524，也不是重复序列化（PR64 已把 search 结果从 172,813 降到 63,820 字符）；是**累计运行时间**超过 900s。
- 1800s 给约 858s 余量，按同一路径应足以收尾；不改变单请求 240s 读超时、50 HTTP、确认≤2、摘要/恢复/Y off。

## 3. 改动

| 文件 | 改动 |
| --- | --- |
| `scripts/go_chi_policy.py` | `chi_admission_seconds` 900 → **1800**；B 180、main read 240、main IO 300 不变 |
| `scripts/go_chi_readiness_inventory.py` | `WINDOWS.chi_admission_seconds` 900 → 1800；`role_runner_timeout_seconds` 1500 → **1900** |
| `scripts/role_runner.py` | 外层 `asyncio.timeout(1500)` → **1900**，让 guard 的 1800 准入先触发，operator 2040 仍能收尾 |
| `profiles/go-chi-entry.json` | time policy 同步 1800 |
| `tests/test_c4_policy_boundaries.py` | 精确 `TIME_POLICY` 断言同步 1800 |
| 文档 | `policy-boundaries.md`、`go-chi-entry-runbook.md`、`go-chi-main-read-timeout/design.md`、task walkthrough/preparation 注记 |

`chi_operator_seconds=1380` 是旧 operator 的**最低**等待，不是上限；`role_operator` 配置仍为 2040，`operator_max_seconds=3600`。`role_runner` 1900 + 实际清理约 10s < 2040；最坏 450s 清理由 operator 2040 硬停兜底。

## 4. 验证计划

1. Docker 内跑定向测试（policy/guard/entry/readiness）与全量 `unittest discover -s tests`；记录 3 个既有 import error（dev 镜像缺 `anthropic`/`docker.types`）与 skip 数。
2. 从当前源码重建 release，记录新 bundle SHA、release manifest SHA、runtime identity；不改旧冻结包。
3. 新隔离 state；新 B（新 identity 必需）；再跑 t015 一次，保持 240s 单请求、50 HTTP、确认≤2、摘要/恢复/Y off；任一 pending/halt/越界/清理不明即停止，不自动重试。
4. 结果写入阶段报告、REVIEW_STATE、tasks 和学习账本；`official_reward=null`。
