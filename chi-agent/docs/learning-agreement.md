# CHI-Bench：边参赛边学习 Agent 开发

建立：2026-10-21；更新：2026-10-31（Asia/Shanghai）。这是用户明确要求长期延续的学习约定和进度入口。新对话先读教学方式、当前进度和下一次入口，追加历史按本轮需要查阅；不能只按代码任务列表推进而忽略教学。

## 用户希望得到什么

在完成 CHI-Bench 竞赛的同时，学习 Agent 如何设计和开发，尤其包括：

- 一个任务怎样拆成 Agent 可以执行的过程。
- 模型、harness、Agent 程序和外部工具分别负责什么。
- harness、Agent 程序和外部工具是怎么设计。
- 怎样发现、选择和调用 tool，参数与返回结果怎样流转。
- 怎样管理执行状态、发现失败并改进流程。
- 怎样用官方评分和对照实验验证改动，而非只看生成的文字。

目标是让用户理解整个项目怎样一步步开发出来，能说明为什么这样设计、代码怎样实现、怎样验证，以及自己实际参与了什么。默认采用 B/C 阶段的完整讲解方式，支持后续复现和面试表达。竞赛仍是主线，学习随实际阶段展开，不另外扩展网页产品或为了教学堆框架。

## 教学方式

**新功能或较大bug修复验收后，集中完成一次完整开发教学，以 B/C 的源码讲解为样板。** 不以零散进度汇报代替教学；围绕一个阶段或一条完整运行流程，先给项目全貌，再逐步进入关键实现，内容较多时按有头有尾的流程分段。模型更换、常规测评和小bug修复不单独展开教学，用户主动追问时再解释；不把每次调整都扩成一课。用户要求“像 B/C 一样讲”时直接完整展开，不只给概念、文件清单或完成汇报。

讲解按以下顺序组织，可随实际阶段调整深度：

1. **放回整个项目**：这一阶段解决什么问题，接住了前一阶段的什么能力，为后续哪一步做准备；输入、输出和本次完成边界是什么。
2. **说明方案与取舍**：从需求解释模块怎样拆分、模型与程序各自负责什么，比较有实际意义的备选方案、采用理由、代价和未验证假设。
3. **沿代码串起主流程**：先给紧凑的数据流或调用图，再从真实入口讲到结果；说明关键文件、函数、配置、状态和数据如何传递，并选关键代码段解释其作用。文件和符号必须在当前源码中核对，不能只照抄实现代理的总结。
4. **走通具体场景**：用一条正常路径说明各模块怎样配合；结合已有证据讲关键失败路径、错误定位、重试与停止、资源清理和结果记录。合成材料、教学示意和真实运行分别标明，没有实现的机制不能说成已经接通。
5. **解释怎样验证和改进**：说明测试为什么覆盖这些行为、独立审核发现过什么问题、如何修复，以及通过证据能证明什么、还不能证明什么；详细命令和结果链接既有审核报告，不复制长日志。
6. **连回后续开发与表达**：说明本阶段留下的限制、与下一阶段的关系，给出能用于复述整个实现的简短讲述提纲。面试表达区分项目实现、AI 辅助分工和用户个人参与，不能把代理执行记成用户亲自完成。
7. **按需继续带读或实践**：用户追问时沿同一流程补讲；用户想动手时，再安排完整场景的代码阅读、Docker 运行观察或有界修改。实践不是默认作业，也不作为继续开发的门槛。

不默认安排选择题、小测或每轮末尾的理解问题；用户主动要求练习、理解检查或模拟面试时再安排。通过用户主动追问、设计讨论、自愿复述和实际操作了解其理解情况，不用零散答题代替项目全貌的讲解。历史中未回答的题目保留为当时记录，不再作为补答清单或下一轮默认任务。

学习记录仍区分“已讲过”“用户能解释”“用户已实践”。没有新增回答或操作证据时如实保留记录，不据沉默或文档交付升级为掌握，也不因此反复要求补答。用户的基础尚未确认，暂按能接触 Python、需要系统理解 Agent 来讲；术语随代码和场景解释，不从简历中出现过某技术就推断已经掌握。

## 随参赛进度展开的学习内容

| 参赛阶段 | 要学习的内容 | 对应的观察或实践 |
| --- | --- | --- |
| 理解官方任务 | 任务输入、角色、可用动作、完成条件；模型与程序的分工 | 用已选官方任务画出输入到评分的过程 |
| 建立官方基线 | harness 做什么；模型调用、tool call、MCP 和工具结果回传 | 跟踪一轮实际请求与响应；未运行前只作概念示意 |
| 分析失败 | 读执行轨迹、区分业务失败与运行失败、定位缺证或错误调用 | 从真实 scorecard 和对应轨迹解释一次失败 |
| 改进 Agent | 状态与阶段设计、规则查阅、上下文、工具约束、校验、重试与停止 | 提出一个通用改进，读关键实现并检查失败路径 |
| 批量实验 | 开发任务与评测任务、固定变量、通过率、可靠性、并发和成本 | 比较同批任务修改前后的实际结果 |
| 冻结与提交 | 配置与依赖复现、来源说明、报告中的证据和限制 | 用户能解释系统设计、个人取舍与实验结论 |

这张表是学习顺序，不表示已经选定编排框架、检索方案、模型或多 Agent 架构。具体方案仍由任务需求和真实基线决定。

## 分工如何配合学习

全项目收尾启动后，执行分工按[本次连续执行计划](../openspec/changes/project-completion/design.md)覆盖下表默认模型安排；DeepSeek 提供真实入口/失败路径和取舍材料，Gemini 对照源码/输出检查，GPT 在可用时集中补充累计讲解。学习仍按上文完整流程开展，不成为继续开发的门槛；模型替换或代理交付不产生用户掌握/实践证据。

| 角色 | 责任 |
| --- | --- |
| 用户 | 在当前对话提需求、参与取舍、阅读材料、追问与验收，按意愿参与完整场景的实践；无需向 Gemini 搬运任务和反馈 |
| Codex 主代理 | 方案/规格、按需协调、独立验收和讲解；把实际实现与设计理由关联起来，只记录关键学习进度并处理 Git 存储 |
| 默认一个 GPT-6.1 Terra / high 实现子代理 | 显式 `gpt-6.1-terra` / `high`，按任务包和文件所有权实现及 Docker 自测，向主代理交付并接受有证据的返工；自测不等于独立验收 |

分工与第二个代理的启用条件以 [当前协作约定](../../COLLABORATION.md#当前协作方式2026-10-27) 和 [实现工作流](subagent-workflow.md) 为准；Git/PR 操作见 [GitHub 工作流](github-workflow.md)。本账本只记录学习内容与理解证据，教学围绕实际材料展开。

未来实现交付应包含：入口与关键调用链、重要文件/符号、一个可解释的工具交互记录、关键取舍及已知失败。Codex 对照真实代码和实际输出讲解，不直接照抄执行器的解释。

正式 trial 必须自主运行。人工教学和调试不能变成评测中的逐题动作指导、补写答案或修改评分结果。示意练习和真实竞赛证据分别记录。

### W：从统一操作者理解一次运行怎样收口

### Y：来源边界能证明什么，不能证明什么

- 这一阶段接住X的“材料主张越界”，但只做一种通用机制：为本次payer运行实际送入主模型请求的instruction和已观察工具文本建立来源ID，核对claim引用的片段边界。它不新增规划器、RAG、审查模型或医疗规则引擎，也不改变账、锁、计费和最终选择动作的人。

### F0–F3：状态来源、角色分支与检索边界

- F1 的核心不是“多存一份日志”，而是把**谁有权说什么**分开：程序只登记本次 run 真实发生的工具 observation（call_id、参数/结果 hash、scope、事件）；模型只能提交事实/计划/缺口，事实和最新业务状态必须引用已登记来源，`source_seq` 由程序填写。这样“模型认为已经提交”和“公开工具回读显示已受理”不会混成一个字段。
- 未知写效果是保守状态，不是错误分类：写类工具 dispatch 失败/结果不可确认才登记 open unknown；只有同目标、更晚的只读 observation 能 resolve。claim 门禁先拦 unknown，再拦“写后未回读”，还拦同批中 claim 之后仍有待执行工具。它仍不证明业务成功，只把“已知未决”从“完成声明”里拆出来。
- F2 没有改官方系统提示，而是用版本化工具返回阶段/分支/停止条件。原因是 `ChiGuard`/`ToolContract` 对 system prompt 和完整工具批次有严格校验；直接拼提示会改变请求契约和身份。代价是模型未必主动调用，真实使用率仍未验证。
- F3 选择“有界、非索引、可回读”的检索，而不是向量库或整本手册灌入：结果只给路径/行号/字节偏移/hash/单行片段，正文仍要 `local-fs-read`；隐藏目录、符号链接、跨 case 和超大结果都拒绝。它解决“定位”，不证明条款适用或语义正确。
- 验证分层：32 个新测试和 5 个合成运行时场景证明契约/接线，不证明真实模型会规划、真实检索命中或业务终态改善。外部 Gemini 尚未审，用户也尚未亲自运行或复述。
- 下一讲解入口：F4 上下文预算/组织与压缩可行性；重点讲“字符/字节不是精确 token”“完整工具批次不能随便删”“历史重写必须版本化”。用户本轮参与目标与边界确认，实际实现/测试由代理完成；不升级为已掌握，不安排默认小测。

### F0–F3 返工：claim 单调、检索范围与“错误不是无匹配”

- 外部 Gemini 的首轮复验说明：只测“正常 claim 通过”不够，还要攻击 claim 之后的状态变化。当前修法是**拒绝 claim 后的写**，把 run 标成 `chi_claim_violation` 并结束为 incomplete；没有把 `journal.run["claim_done"]` 改回 false。原因是 journal 是单调证据，F1 契约明确不因新状态重写旧 claim；如果为了“看起来干净”回写历史，就会破坏“原始 claim/账目不被改写”的审计边界。
- 检索的三个边界要分开：路径是否在角色允许范围、是否属于当前 target case、读取失败是否有明确错误。`allowed_read()` 只解决第一层；workspace 里其他 case 仍符合命名规则，所以必须再核对 `target.case_id`。单文件损坏与“目录里没有关键词”是两种事实，前者必须返回 `ERROR: search_unreadable`，不能伪装成 `no_matches`。
- target 未设定时禁止 case scope 事实，是为了避免一份状态同时吸收多个 case 的观察；先确定目标，再让事实挂到该目标上。
- 返工证据：定向 38 tests、全量 424 tests（2 个既有环境错误、8 skipped）；外部 Gemini 首轮是真实 Docker 复验，返工后的复审仍待完成。
- 下一讲解入口仍是 F4：上下文预算/组织与压缩可行性；重点讲“完整工具批次不能随便删”和“历史重写必须版本化”。

### F0–F3 复审通过的含义

- “通过”只覆盖离线静态审查、契约一致性和 Docker 内合成 MCP/HTTP 回归；没有调用真实模型、没有官方判分、没有未见题。它证明的是实现与契约在合成边界上闭合，不是业务效果或临床正确性。

### F4–F6：预算、完成证据与失败恢复

- F4 先把“上下文里有什么”变成可测数据：system、instruction、tools、history、tool_result、reasoning 分开计字符，再给字节和 `chars/4` 的估计 token；不把估计冒充 tokenizer。预算在 `journal.reserve()` 前检查，超限直接停止，不产生请求。`context.jsonl` 只存计数，不复制正文。
- 自动压缩没有采用，原因是 `ToolContract.validate_history()` 要求完整已接受工具批次；要合法换历史，需要新 contract 版本、reasoning/tool 关联重放、替换 hash、旧检查点防覆盖和真实 SDK/API 证据。当前交付的是测量、预算、状态/片段组织和超限停止，不是“压缩已完成”。
- F5 的完成报告把 `mechanical_pass`（机械/来源通过）、`not_applicable`（没有可核验效果）和 `blocked`（缺口/未知/违规）分开；业务效果再分 `observed/not_observed/not_verified/unknown/violation`。claim 仍是模型声明，报告不是临床或官方 verdict。
- F6 的未知写不是“失败”也不是“成功”：MCP 写异常返回 `UNKNOWN_WRITE_EFFECT`，登记 open unknown；期间禁止再写，只能用同目标更晚只读观察 resolve；未解决就结束则 run 为 `chi_unknown_write_effect` incomplete。重复读第 3 次警告、第 5 次阻断；重复写第 2 次阻断，不自动重试。
- 验证：定向 37 tests、全量 436 tests（2 个既有环境错误、8 skipped）；真实 tokenizer、真实 MCP 超时副作用、真实模型是否遵守停滞提示仍未验证。
- 下一讲解入口：F7 实验清单/分母/费用汇总与 Z1 正式配送准备；真实运行审批包另行准备。

### F4–F6 复审通过的含义

- 外部 Gemini 的通过覆盖四项：F4 预算/度量、F5 完工检验、F6 未知写恢复、F6 停滞保护；边界仍是离线静态/契约与 Docker 合成，没有真实模型、官方判分或未见题。
- 这次通过不改变“自动压缩不采用”的决策；压缩设计按讨论搁置，以后单独做确定性检查点/可选摘要变更。
- 面试可讲：预算为什么在 dispatch 前拦、完成报告为什么只做机械验证、未知写为什么先阻断再只读查证、停滞为什么只给信号/有限阻断而不自动重试。具体代码走读可参照 [F0–F3 走读](f0-f3-walkthrough.md) 的同一方式补 F4–F6。
