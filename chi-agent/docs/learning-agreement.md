# CHI-Bench：边参赛边学习 Agent 开发

建立与更新日期：2026-10-21（Asia/Shanghai）。这是用户明确要求长期延续的学习约定和进度入口。新对话先读本文件，再结合项目最新状态继续；不能只按代码任务列表推进而忽略教学。

## 用户希望得到什么

在完成 CHI-Bench 竞赛的同时，学习 Agent 如何设计和开发，尤其包括：

- 一个任务怎样拆成 Agent 可以执行的过程。
- 模型、harness、Agent 程序和外部工具分别负责什么。
- harness、Agent 程序和外部工具是怎么设计。
- 怎样发现、选择和调用 tool，参数与返回结果怎样流转。
- 怎样管理执行状态、发现失败并改进流程。
- 怎样用官方评分和对照实验验证改动，而非只看生成的文字。

目标是让用户能理解、参与取舍、复现并解释系统。竞赛仍是主线，学习随实际阶段展开，不另外扩展网页产品或为了教学堆框架。

## 教学方式

每轮重要推进采用以下顺序，可按用户反馈缩短或展开：

1. **讲当前问题**：这一步要解决什么竞赛问题，输入和预期可观察结果是什么。
2. **讲设计理由**：解释可选方案、采用某方案的理由、代价和待验证假设。用清楚的数据流或小图串联过程。
3. **看一段实际材料**：结合已核对的任务、工具契约、关键源码或真实轨迹。没有实现时，示意代码必须标明尚未实现和未执行。
4. **实践与验收**：说明实际做了什么、哪里成功或失败、用什么证据判断；引导用户阅读关键记录，适当安排小修改或运行观察。
5. **确认理解**：一次给一个小问题，让用户复述、预测下一步或定位一个错误。先听回答，再反馈；用户希望直接推进时可跳过。
6. **更新进度**：记录本轮讲了什么、用户的疑问、实际理解证据和下一步，不把“文档已交付”当作“用户已学会”。

默认每次聚焦一到两个概念，不一次倾倒完整源码或整套术语。不要求用户先学完所有内容再推进竞赛，也不因未完成自测而自动暂停已授权工作。

用户的基础尚未确认。暂按能接触 Python、但需要系统理解 Agent 来组织讲解；根据实际回答调整，不从简历中出现过某技术就推断已经掌握。

## 随参赛进度展开的学习内容

| 参赛阶段 | 要学习的内容 | 对应的观察或实践 |
| --- | --- | --- |
| 理解官方任务 | 任务输入、角色、可用动作、完成条件；模型与程序的分工 | 用已选官方任务画出输入到评分的过程 |
| 建立官方基线 | harness 做什么；模型调用、tool call、MCP 和工具结果回传 | 跟踪一轮实际请求与响应；未运行前只作概念示意 |
| 分析失败 | 读执行轨迹、区分业务失败与运行失败、定位缺证或错误调用 | 从真实 scorecard 和对应轨迹解释一次失败 |
| 改进 Agent | 状态与阶段设计、规则查阅、上下文、工具约束、校验、重试与停止 | 提出一个通用改进，读关键实现并检查失败路径 |
| 批量实验 | 开发任务与评测任务、固定变量、通过率、可靠性、并发和成本 | 比较同批任务修改前后的实际结果 |
| 冻结与提交 | 配置与依赖复现、来源说明、报告中的证据和限制 | 用户能解释系统设计、个人取舍与实验结论 |

这张表是学习顺序，不表示已经选定编排框架、检索方案、模型或多 Agent 架构。具体方案仍由任务需求和真实基线决定。

## 分工如何配合学习

| 角色 | 责任 |
| --- | --- |
| 用户 | 提问、参与取舍、阅读关键材料、用自己的话解释、检查结果；逐步承担适合当前程度的小实践 |
| Codex | 同时负责方案/规格/独立验收和讲解；把实际实现与设计理由关联起来，及时记录学习进度 |
| DeepSeek（计划中的实现执行器） | 在恢复编码后按规格实现、自测并提供可追踪的交付记录；其代码仍须审查，不因自述完成就当作学习或验收事实 |

未来实现交付应包含：入口与关键调用链、重要文件/符号、一个可解释的工具交互记录、关键取舍及已知失败。Codex 对照真实代码和实际输出讲解，不直接照抄执行器的解释。

正式 trial 必须自主运行。人工教学和调试不能变成评测中的逐题动作指导、补写答案或修改评分结果。示意练习和真实竞赛证据分别记录。
