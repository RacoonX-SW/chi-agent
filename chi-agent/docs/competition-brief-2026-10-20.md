## 比赛实际要求做什么

开发一个自主 Agent，在官方 χ-World 模拟环境中读取病例、查阅手册、调用允许的 MCP/REST 工具并完成业务任务。官方提供模拟环境、任务和评测器；参赛方可以选择或改进模型、Agent harness、提示词、编排及工具使用策略。规则不要求从头训练模型，也不指定必须自建网页或采用某个 Agent 框架。

公开开发集包含 75 个基础任务，每领域 25 个：

| 领域 | 任务含义 |
| --- | --- |
| Provider Prior Authorization | 医疗机构侧准备和办理授权申请 |
| Payer Utilization Management | 保险方受理、依据规则审查和作出裁决 |
| Care Management | 病例审阅、模拟沟通、评估和照护计划 |

正式私有评分会汇总三个领域，也报告分领域结果。医院侧适合作为起步调试范围，争取整体排名时需要考虑其余领域。不得把公开目录中的 E2E/Marathon 扩展任务数，误当成竞赛的 75 个基础任务清单。

开发、配置和调试允许人工参与；被评测的单次 trial 开始后必须由系统自主完成，不能由人逐步选动作、补答案或修产物。Agent 不得读取隐藏预期、参考答案或仅评测器可见的文件。

## 如何评分

- 单任务官方严格二值 reward：全部必需且适用的检查通过才为 1，否则为 0；部分完成率只用于诊断。
- 私有主分数 pass@1：每个任务第一次尝试的通过率，不是三次中挑最好的一次。
- 主办方每个私有任务运行 3 次独立尝试；pass^3 是三次全部通过的任务比例，用于可靠性和同分比较，不是 pass@3。
- 同分按 pass^3、平均 Agent 推理成本、平均工具调用数、较早有效最终提交的顺序比较；成本不可比时按规则跳过该项。
- 私有任务由主办方运行，采用冻结的同一套参赛配置；最终排名以其结果为准。

## 必须交付的三项材料

依据 Rules 第 9、11 条：

| 材料 | 内容与渠道 |
| --- | --- |
| Kaggle Writeup | 队名、方法摘要、模型名和复现概要；在 Kaggle 发布，作为参赛作品记录 |
| 私有可运行程序包 | 自有 Agent/编排源码、提示词、工具与配置、依赖和锁文件、精确模型/API 标识、外部资源说明、完整运行说明或带说明的容器镜像 |
| 技术报告 | 说明系统、方法、外部资源及已有实验结果；IEEE 双栏，不超过 5 页，参考文献不计入页数 |

程序包和报告或其下载链接发送至 `research@actava.ai`；邮件主题以 `[Kaggle]` 开头，包含队名及 Kaggle Writeup 链接。程序包附已有公开运行证据和成本记录（如果运行过）。不提交凭据、手册副本或受保护内容；无需提供不属于自己的第三方专有模型权重。

源码不必为了参赛公开到 GitHub。独立 CHI-Bench evidence leaderboard 的 PR 提交是可选流程，不能替代 Kaggle 竞赛最终材料。

## 概览和 Rules 的差异

Overview 的 Evaluation 段仍描述含 `task_id,reward` 的 75 任务 CSV，以及 Data tab 将提供模板。但实际当前页面为 Community Hackathon；本次未登录视图有 Overview、Writeups、Code、Discussion、Rules，未看到 Data/预测上传入口。

Rules 第 9 条明确写公开结果可选、不要求跑完全部公开任务；第 11 条明确不要求完整 75 任务公开审计包，独立 evidence leaderboard 也是可选。当前准备以这些明确 Rules 条款为依据：三项最终材料是主线，不把全量 CSV 当成已确认的强制要求。临近提交时复核主办方公告；如仍有冲突，再确认实际提交流程。不能替未运行任务填写 reward，也不能用自估值或修改过的值报分。
