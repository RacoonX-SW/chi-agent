## 后续分工

2. 子代理按授权完成自测并停止写入，主代理固定完整候选；共享文件由一个子代理独占写入、完成后交接，分析可并行。当前只恢复 D0，A/B/C、参赛模型 API 和官方判分仍暂停。
3. 主代理按差异独立审核并记录结果，问题交回对应子代理；检查上传范围、显式暂存/commit 后推送该工作分支，创建 base=main 的 PR，说明问题、最终行为、实际检查和限制。未完成实现可用 draft；交付用户审核时明确可审查状态。
4. 用户审核 PR、提出意见并决定是否合并 main；主代理不点击 Merge、不执行合并命令、不启用自动合并。返工推到同一分支并说明新 SHA，改动后旧审核结论不能覆盖未经检查的新提交。
5. 用户合并后，主代理在下一次任务中核实远端实际结果并同步；下一任务从最新 origin/main 新建分支。PR 未合并时不夹带新任务到原分支，也不默认从未合并分支继续堆叠。普通 push/PR 创建、内部代码通过与用户合并分别记录；公开发布、Kaggle 提交和付费运行按各自授权处理。

## 分支到合并的顺序

1. 记录干净或已有改动的起点及 `origin/main` SHA；保留其他工作，不 reset 或全量暂存。
2. 在写文件前创建/切换 `codex/<任务名>`，核对当前分支不是 main。两个子代理沿用这个任务分支，Git 由主代理统一管理；他们不自行切分支。
3. 实现、Docker 内自测、固定候选及主代理独立检查均在该分支进行，审核/学习文档也提交到同一任务分支。
4. 显式推送，例如本次的 `git push -u origin codex/branch-review-workflow`；创建 base=main、head=任务分支的 PR，交用户查看 Commits、Files changed、检查证据和限制。
5. 用户决定合并；主代理等用户通知或下一次接续时核实，不后台轮询 PR，也不代行合并。之后同步 main，再为下一任务另建分支。

`push` 只更新选定的远端分支，PR 提供与 main 的差异；只有合并才把改动纳入 main。当前是协作约定，没有另行配置 GitHub 分支保护规则。若连接器/浏览器权限不足无法自动创建 PR，应先完成工作分支推送，明确报告阻塞并提供 compare 链接，不能声称 PR 已创建。

当前任务中由主代理等待内部交付并推进审核；任务结束后没有后台自动验收或轮询安排，无需用户复制子代理整段对话。

## 推荐路径：本地交接，按提交审核

当前三个代理使用同一个已有 Git 仓库及任务分支：主代理管规格/文档/Git，两个 Luna 子代理分阶段拥有实现文件，同一时段只有一个实现写入者。完成自测后停止修改，避免审核过程中代码继续变化；由主代理统一提交、推送工作分支及创建 PR，不要求每个子代理各建一个 PR。

按 [D0 接续 Prompt](d0-handoff-prompts.md) 固定起点，先实现、停止、固定候选，再独立审核；必要返工仍由这两个子代理接力。若以后审核旧候选时继续开发，需要独立 worktree/checkout 和隔离的测试容器/结果目录；仅切换分支不足以隔离文件，合并后仍须验证。

实现方只需维护一份简短阶段交付报告，包含：

- 任务/阶段、两个子代理的请求模型/推理设置与实际任务身份、起始基线 SHA、候选 SHA，以及仍有的未提交改动；SHA 必须对应实际交付文件。主代理固定基线，子代理接手时核对实际 HEAD/差异，不得暂存或丢弃其他代理的工作。
- 主要变更文件和各自目的，指出相关生产入口及必要的设计取舍。
- 实际在 Docker 内运行的检查命令、工作目录、退出结果与日志位置；未运行项、失败项和限制。

按既有 handoff 使用 `reviews/bootstrap-baseline-d0-handover.md` 等阶段报告，不同时另写一套长总结、重复 JSON 和全文日志。真实试跑阶段才附该阶段所需的运行证据。原始日志留在忽略目录，审核按需读取相关片段。

当前对话继续开发的示例（旧 Gemini 手工通知模板已被替代）：

```text
请用两个 Luna High 子代理继续 bootstrap-baseline/D0。
先接上 REVIEW_STATE.md，按未决问题分工，重叠文件串行改。
你负责协调、独立审核、教学和 GitHub 备份；A/B/C 继续暂停。
```

Codex 的读取顺序：

1. 核对项目当前摘要、[审核接续状态](../reviews/REVIEW_STATE.md)、Git 状态和候选身份，确定本轮涉及的规格。首次 D0 仍需建立现有实现的可信认识；历史候选未通过，不能直接视为已审通过的基线。
2. 从 Git 根目录查看 `git diff --stat <基线> <候选>` 和 `git diff --name-status <基线> <候选>`，确认完整改动范围，包括根目录指令与依赖文件；再按相关路径读取具体差异。
3. 用差异和符号检索定位相关入口、调用者、配置与测试，读取必要上下文。接口、依赖、权限、持久化或架构变化可扩大检查范围；不承诺只看几行 diff，也不默认读取全仓库、第三方源码和整段执行器对话。
4. 对照标准在 Docker 内重跑有意义的检查，复用已核对的历史证据定位问题；不因审核自动重复付费 trial。若候选与当前工作区不同，先取得隔离、可复现的候选环境，不重置他人改动，也不把当前工作区测试结果记到另一提交。
5. 在一份审核报告中给出问题、检查证据和未验证项，更新审核接续状态。返工时优先比较上次已审候选与新候选，同时核对遗留问题和累计阶段目标；阶段最终通过要对应完整候选，不能遗漏更早未通过的差异。

没有 commit 仍能审查，但须保存可复核的 patch/文件摘要，并列明跟踪和未跟踪的交付文件，不能只报 HEAD。固定提交是更简单的默认交接方式。报告和审核摘要用于定位材料，不能替代源码与检查证据。

## 本地与 GitHub 怎么选

| 路径 | 适用情况 | 可审查的材料 |
| --- | --- | --- |
| 直接读取本地 Git | 子代理交接与主代理独立检查 | 工作分支提交、必要工作区差异；检查可在 push 前完成 |
| GitHub 工作分支 / PR | 后续交付用户审核与合并的默认入口 | 已推送候选相对 main 的差异、说明及检查结果；用户决定合并 |

两条路径都可按差异审核。GitHub 本身不会让模型免读代码；减少重复输入主要靠任务范围、稳定提交、精简交付和可靠的审核接续记录。新对话仍需读最小必要上下文，不承诺固定 token 节省比例或完整缓存。

Codex 官方也提供本地 `/review` 的“对比基线分支”和“审查未提交改动”入口；这是可选操作，本项目仍按固定候选和 OpenSpec 做验收。见 [官方本地审核说明](https://learn.chatgpt.com/docs/code-review#review-in-the-app)。

## commit 和 push 的区别

`commit` 在本机 Git 历史中保存一个版本；`push` 将选定分支的提交发送到 GitHub。执行器只做本地 commit，其他电脑或新执行器仍需访问同一本机目录，或者等 push 后再从 GitHub 获取。两者都不能证明代码正确。

接手时检查 `git status`、`git log`、`git remote -v` 与分支的上游状态；不要重置或覆盖他人未提交的工作。GitHub 不是本次竞赛的自动提交入口。
